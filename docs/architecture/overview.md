# Архитектура MIRA Core 0.1

Ядро поставляется как исполняемый файл `mira`. Общая логика доступна также
как Rust-библиотека из `core/src/lib.rs`. Внешние брокеры, облачные сервисы
и конкретный пользовательский интерфейс для неё не требуются.

```text
CLI ─────────────┐
                ├── service.rs ── system.rs ── системные API ОС
Web UI → HTTP ──┘

CLI / запуск сервера → config.rs → config/ и data/
Все компоненты → tracing → stderr + logs/
```

## Компоненты

| Файл | Ответственность |
| --- | --- |
| `core/src/lib.rs` | Публичные модули и единая версия из Cargo.toml |
| `core/src/service.rs` | Модели status/version, точка входа в системную диагностику |
| `core/src/system.rs` | Сбор CPU, памяти, дисков и сети через sysinfo |
| `core/src/config.rs` | Пути, TOML, валидация, сохранение и блокировки |
| `core/src/main.rs` | CLI-адаптер, текст/JSON, запрос статуса работающего сервера |
| `core/src/http.rs` | HTTP-адаптер, маршруты API, встроенные статические файлы |
| `core/src/logging.rs` | Уровень, вывод в stderr, файловая ротация |
| `web/` | Диагностический клиент API без сборщика и внешних ресурсов |

Модули библиотеки не импортируют CLI, HTTP или Web UI. `mira system` и HTTP
вызывают `service::system()`, `mira version` и HTTP — `service::version()`.
`mira status` обращается к серверному status endpoint и выводит его модель.
Статус работающего сервера создаётся функцией `service::status(CoreStatus::Ok)`.
У CLI имеются дополнительные состояния stopped/unreachable для отсутствующего
или недоступного серверного процесса. Запущенный HTTP-сервер не имитируется CLI.

Состояние `ok` означает, что HTTP-обработчик ядра отвечает. Это не агрегированная
оценка будущих модулей или внешних соединений.

## Жизненный цикл

1. CLI разбирает аргументы и выбирает корневую папку данных.
2. Папки создаются, конфигурация читается или создаётся при отсутствии.
3. Настраивается логирование с выбранным уровнем.
4. Информационная команда выполняется и завершает процесс либо `serve` берёт
   блокировку экземпляра, открывает TCP listener и сохраняет текущий адрес.
5. При Ctrl+C / SIGTERM сервер прекращает приём соединений, завершает текущие
   HTTP-запросы; файловый лог сбрасывается, блокировка освобождается.

ОС освобождает файловую блокировку также при аварийном завершении процесса.
Файл блокировки может оставаться на диске — его наличие само по себе ничего
не говорит о состоянии ядра. Во время короткого окна запуска `status` может
показать unreachable, пока HTTP ещё не начал отвечать.

## Системные данные и переносимость

Используется sysinfo для Windows и Linux. Обход процессов и запуск системных
shell-команд не нужны. Системные данные запрашиваются заново при каждой команде
или HTTP-запросе. В HTTP сбор перенесён в `spawn_blocking` и ограничен семафором,
чтобы операции ОС не блокировали обработчики status/version.

Набор полей и единицы измерения одинаковы для CLI JSON и HTTP JSON. Динамические
значения RAM и свободного места могут различаться между последовательными запросами.
Список устройств ограничен видимостью ОС и разрешениями пользователя. На ARM
название процессора может быть недоступно; это отражается в `warnings`.

## Сохранение

`config.lock` защищает всю операцию read-modify-write между процессами MIRA.
Запись временного файла, `sync_all` и `persist` предотвращают чтение наполовину
записанного TOML. Некорректный существующий файл не перезаписывается автоматически.
Сервер читает настройки при старте; горячая перезагрузка в 0.1 не входит.

Сведения о текущем listener лежат в `data/endpoint.json`. Они используются только
пока межпроцессная блокировка указывает на активный сервер. Поэтому смена порта
в конфигурации не меняет адрес уже работающего экземпляра для `mira status`.

## HTTP и браузер

В 0.1 API предоставляет только чтение. По умолчанию слушается loopback,
аутентификации и TLS нет. Браузер загружает сведения с того же origin;
внешние скрипты и CORS не нужны. Динамический текст выводится через `textContent`.
Ответы снабжены `no-store`, `nosniff` и Content Security Policy.
