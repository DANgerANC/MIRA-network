# MIRA Core 0.1.0

Самостоятельное ядро на Rust: CLI, сведения о системе, постоянная конфигурация,
логи, HTTP API и встроенная диагностическая страница. Для работы не нужны
Thundercloud, MQTT, Node.js или внешние сервисы.

Нативная release-сборка и автоматизированная проверка выполнены на Windows 11 x86-64
(GNU toolchain, 1 октября 2026, 28 проверок) и Linux Mint 22.1 x86-64
(3 октября 2026, 31 проверка). CLI, HTTP API, конфигурация, блокировки и перезапуск
работают на обеих ОС; на Linux проверены SIGTERM и SIGINT.
[Отчёт и границы проверки](docs/cross-platform-2026-10-03.md).
Linux ARM64 также проверен 3 октября 2026 в QEMU: кросс-сборка и 31 проверка
в Ubuntu ARM64 прошли. [Отчёт об эмуляции](docs/arm64-qemu-2026-10-03.md).
Android ARM64 проверен на физическом Xiaomi 21081111RG с Android 14:
31 проверка через ADB shell прошла. [Отчёт Android](docs/android-2026-10-03.md).
Запуск в APK, физическое Linux ARM64-устройство и Windows MSVC ещё не проверены.
Ранее проведена [демонстрация Windows с Web UI](docs/demo-windows.md).
Полный сценарий приёмки: [docs/acceptance.md](docs/acceptance.md).

## Локальная сборка в подготовленной среде Windows

В этом проекте инструменты Rust/MinGW расположены в `.tools/`.
Для повторной release-сборки выполните `.\build.ps1` из корня проекта.
Готовый файл: `target\release\mira.exe`. Системный PATH менять не нужно.
Демонстрационные данные находятся в `C:\MIRA\.mira`; для обращения к работающему
демонстрационному серверу используйте `--home C:\MIRA\.mira`.

## Сборка и запуск

Нужен актуальный стабильный Rust с Cargo; минимальная заявленная версия ядра —
Rust 1.88. Для Windows используйте MSVC toolchain и C++ Build Tools / Windows SDK,
для Linux — системный C linker (`cc`, например из `build-essential` в Debian/Ubuntu).
Первая сборка скачивает зависимости из crates.io. После неё ядро работает локально.

Из корня репозитория:

```sh
cargo build --release
```

Windows PowerShell:

```powershell
cd C:\MIRA
.\target\release\mira.exe version
.\target\release\mira.exe system
.\target\release\mira.exe config
.\target\release\mira.exe serve
```

Linux:

```sh
./target/release/mira version
./target/release/mira system
./target/release/mira config
./target/release/mira serve
```

При желании установите команду в Cargo bin:

```sh
cargo install --path core
mira version
mira serve
```

Для короткой команды `mira` каталог Cargo bin должен входить в `PATH`.
`serve` работает в текущем терминале. Остановка — Ctrl+C, на Linux также SIGTERM.
Автозапуск через Windows Service / systemd в 0.1 не входит.

Откройте [диагностику MIRA](http://127.0.0.1:8787) после запуска сервера.
HTML, CSS и JavaScript встроены в исполняемый файл: папка `web/` нужна при сборке,
но не при переносе готового бинарного файла. Изменение страницы требует пересборки.

## CLI

| Команда | Назначение |
| --- | --- |
| `mira version` | Версия текущего исполняемого файла |
| `mira status` | Состояние сервера, использующего эту папку данных |
| `mira system` | ОС, архитектура CPU, модель CPU, RAM, диски, интерфейсы и IP |
| `mira config` или `mira config show` | Текущая конфигурация в TOML |
| `mira config paths` | Реальные пути конфигурации, данных и логов |
| `mira config set KEY VALUE` | Проверить и сохранить настройку |
| `mira serve` | Запустить API и диагностическую страницу |

`--json` поддерживается для всех информационных команд и `config set`.
Например: `mira system --json`, `mira status --json`.
Результат идёт в stdout, логи и сообщения об ошибках — в stderr.

У работающего сервера `mira status` выводит:

```text
MIRA Core 0.1.0
Status: running
```

`mira status --json` получает JSON непосредственно от `/api/v1/status`:

```json
{"core":"0.1.0","status":"ok"}
```

Если сервер не запущен, статус — `stopped`; если процесс держит блокировку,
но HTTP недоступен — `unreachable`. Код выхода `status`: 0 для `ok`, 1 для остальных
состояний или ошибки. Ошибки разбора CLI имеют код 2. Сама команда `status` сервер не запускает.
При остановленном сервере поле `core` содержит версию CLI, при запущенном — ответ сервера.
Все команды должны использовать один и тот же `--home`, если он был указан.

## Постоянная конфигурация

При первой содержательной команде создаются:

```text
<MIRA_HOME>/
├── config/
│   ├── mira.toml
│   └── config.lock
├── data/
│   ├── server.lock
│   └── endpoint.json   # появляется при запуске сервера
└── logs/
    └── mira.YYYY-MM-DD.log
```

Каталог по умолчанию: `%LOCALAPPDATA%\MIRA` на Windows и
`$XDG_DATA_HOME/mira` либо `~/.local/share/mira` на Linux.
Приоритет выбора: `--home` → переменная `MIRA_HOME` → каталог пользователя.
Относительный `--home` разрешается относительно текущей рабочей папки.
Флаги `--help` и `--version` обрабатывает Clap до создания папок.

```sh
mira --home ./.mira config
mira --home ./.mira serve
```

Начальный `config/mira.toml`:

```toml
schema_version = 1
node_name = "MIRA"

[http]
host = "127.0.0.1"
port = 8787

[logging]
level = "info"
```

```sh
mira config set node_name PC-01
mira config set http.port 9090
mira config set logging.level DEBUG
```

Поддерживаются только `node_name`, `http.host`, `http.port`, `logging.level`.
HTTP host — числовой IPv4/IPv6 адрес; port — 1–65535. Уровень логов сохраняется
в нижнем регистре. Неизвестные поля, неверные значения и неподдерживаемая версия
схемы считаются ошибкой. Повреждённая конфигурация не заменяется настройками по умолчанию.

Изменения применяются к серверу после его перезапуска. Пока он работает,
`status` использует сохранённый адрес текущего процесса из `data/endpoint.json`,
поэтому изменение будущего порта не ломает запрос статуса. Старый endpoint-файл
после остановки игнорируется: наличие файла не считается признаком работы ядра.
Одна папка данных допускает один сервер; для нескольких экземпляров нужны разные
папки и порты.

Запись настроек выполняется под межпроцессной блокировкой через временный файл
в том же каталоге, синхронизацию и замену целевого файла. На Unix дополнительно
синхронизируется каталог. Гарантии относятся к обычному локальному файловому
хранилищу; сетевые файловые системы в 0.1 не поддерживаются как папка данных.
Ручное редактирование TOML делайте при остановленном ядре и без параллельного `config set`.

## Логи

Уровни: ERROR, WARN, INFO, DEBUG. По умолчанию INFO и более важные события.
Логи пишутся в stderr и в файлы с суточной ротацией, с лимитом хранения 14 файлов.
DEBUG добавляет сведения о сборе системных данных и HTTP-запросах.
Очередь записи сбрасывается при обычном завершении. Ошибки до настройки логирования
(например, недоступная папка или повреждённый TOML) выводятся в stderr.

## HTTP API v1

| Метод и путь | Ответ |
| --- | --- |
| `GET /api/v1/status` | `{"core":"0.1.0","status":"ok"}` |
| `GET /api/v1/version` | `{"core":"0.1.0"}` |
| `GET /api/v1/system` | Системный отчёт, полученный из общей логики ядра |

В системном отчёте:

- `os`, `os_version`, `architecture`, `hostname`;
- `cpu.model`, `cpu.logical_cores`, `cpu.physical_cores`;
- `ram_total_bytes`, `ram_available_bytes`;
- `disks[]`: имя, точка подключения, общий и свободный объём в байтах;
- `network_interfaces[]`: имя, MAC, IPv4/IPv6 с длиной префикса;
- `local_ips[]`: уникальные адреса без loopback, unspecified и multicast;
- `warnings[]`: сведения, которые ОС не смогла предоставить.

Свободное место показано отдельно для каждой точки подключения, без суммирования
томов. CLI и браузер показывают GiB (1024³ байт). Названия ОС, CPU и интерфейсов
берутся у операционной системы; неизвестные значения не подменяются выдуманными.
Архитектура `x86_64` означает x86-64, `aarch64` — ARM64. Виртуальные машины и
контейнеры сообщают доступные им ресурсы, которые могут отличаться от физического хоста.

Одновременно выполняется один HTTP-запрос системных данных. При занятом сборщике
возвращается 503 с `{"error":"system_query_busy"}`; клиент может повторить запрос.
При ошибке фоновой задачи — 500 с `{"error":"system_query_failed"}`.
Неизвестный маршрут возвращает 404. Диагностическая страница обновляется раз в 5 секунд.

По умолчанию API слушает только `127.0.0.1`. Аутентификация и TLS в 0.1 отсутствуют.
Настройка `http.host = "0.0.0.0"` открывает диагностику на доступных IPv4-интерфейсах;
делайте это только в доверенной сети. API только читает сведения, изменять конфигурацию
можно через локальный CLI.

## Архитектура и границы 0.1

Подробности: [обзор архитектуры](docs/architecture/overview.md),
[план развития](ROADMAP.md), [приёмка на целевых ОС](docs/acceptance.md).
Windows x86-64 и Linux x86-64 — обязательные цели приёмки; Linux ARM64 — дополнительная.
Совместимость проверенного сценария подтверждена нативной сборкой и запуском на
Windows GNU и Linux x86-64; Linux ARM64 проверен запуском в QEMU после
кросс-компиляции. Android ARM64 проверен на физическом телефоне через ADB shell;
запуск в sandbox обычного Android-приложения не проверен.
`Cargo.lock` создан при демонстрационной сборке и сохранён в корне проекта.
Для повторной сборки зафиксированных зависимостей используйте `cargo build --release --locked`.
